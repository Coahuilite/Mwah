# VNPE 条件加载与下一阶段计划

后续路由：维护者已将范围扩大为全模组共享内容／双原生构建与隐式状态机整理，当前待对齐计划由[新 proposal](../shared-content-and-lifecycle/proposal.md)负责。本页保留前期研究及版本评估，不再作为独立待实施计划；minor 内兼容根的旧布局草案由新候选取代。

状态：2026-11-09 调研／开发计划，尚未实施。维护者接受共享源码＋分开原生构建，并要求调研 Wiki、规划 VNPE 的 LoadFolders 隔离、完成当前本地提交及评估下一 minor。本轮不改运行加载结构，不推送或发布。

## Why

当前三个 VNPE 出口已在独立 C# 文件中按包启用查询隔离，但识别代码仍随主程序集加载，专用文案也在基础机器语言文件中。下一步应利用宿主的条件内容加载，令未启用 VNPE 的组合连兼容登记都不载入，而不是仅仅把源码移到另一个文件夹。

## What Changes

- 在每个 minor 内增加由 `IfModActive="VanillaExpanded.VNutrientE"` 控制的兼容内容根。
- 将三个目标身份、接近策略及专用文案迁入该内容根；用小型 Mwah 自有登记 Def 驱动共享识别，不修改 VNPE 的 Def。
- 主程序集保留通用登记消费和现有 Paste 规则，不带 VNPE 包／目标名字，不新建核心或兼容 DLL。
- 同步暂存、有效加载选择、本地化及现有符号清单检查；只改真实受影响的检查前提。

具体目录、连接与风险见 [design](design.md)。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

无玩家保证变化；以 ADD-13～19、NATIVE-01～04 为原合同做内部重构，零 delta。原版营养膏机、Tap／Feeder／Dripper、PowerOn、站位、单槽、识智、饱腹概率、冷却和存档身份全部保留。若实施发现必须改变任一保证，先提交具体冲突，不借重构改写规格。

## 建议推进模组 0.4.0，不立即切版

这里的下一 minor 指模组 `0.3.x → 0.4.0`，不是增加 RimWorld 1.8 支持。

**值得推进 0.4.0。** 相比已发布 0.3.0，机器类别、研究设备识智收益、原版营养膏饱腹及三个可选出口都是新增玩家能力，不宜把整批功能当作修补版；LoadFolders 隔离是这批功能的交付完善，不单独撑起一个 minor。维护者已确认亲吻点及识智观察，可复用其证据。

本轮不修改 csproj／About／changelog／工坊版本，不创建 `0.4.x` 或 tag。版本与发布面联动留到隔离实现范围获准、候选交付方案确定后一次完成；未接受的版本计划不写进发布日志。

## 下一步实施顺序

1. **登记消费闭环**：定义仅服务营养膏吻的目标登记；由 Def 加载期消费，通用 worker 根据目标决定前向或接触策略。保持原版四个精确特例和默认工作台类型族。
2. **条件内容闭环**：将 VNPE 三条登记及专用中英文案放入兼容根，更新两版 LoadFolders。移除旧硬编码 adapter 后才删除其真实符号清单项，不保留空类或新增 DLL。
3. **交付闭环**：调整已有暂存／验证的内容集合和条件解释；基础组合与 VNPE 组合分别检验有效输入，继续保持一个生效的 Mwah.dll、不出现重复 Def／语言键。使用既有工具，不添加单元测试或等价换名用例。
4. **原生消费确认**：维护者用同一个新候选包，在 1.6／1.7 分别确认 VNPE 缺失时无兼容登记／缺失错误、启用时三出口可进入原 Paste 链。聚焦此次加载变化，包含 Tap 及接触目标的关键请求和旧记忆／Job 继续解析；不重开已通过的识智数值观察。
5. **版本收口**：确认候选接受范围后再决定正式 0.4.0 版本轴与渠道准备；发布另行授权。

## 完成条件与恢复

实施者负责源码、内容、脚本和说明的一致修改；维护者负责实际安装及原生验收。原有受支持目标／入口／JobDef／ThoughtDef／设置键不改名，运行配置不增加前提。兼容登记缺一个外部 Def 时仅诊断并跳过该项，其他目标和基础玩法继续可用。

采用新加载布局前保留本轮提交的现有实现作为可检索基线；若迁移失败，以普通修复提交恢复受影响的连接，不重写历史、不改第三方安装、不碰用户存档。当前阶段的交付是此计划与已完成功能的本地提交，不是新布局已经可用。
