# 整理设计与跨版本架构评估

评估日期：2026-11-09。适用范围：整理阶段 `bedea41` 基线、固定引用 `1.6.4871`／`1.7.4990-unstable`。这里解释当时的实现和取舍，现行保证仍由[规格入口](../../../docs/specification.md)指向。

本页保留迁移前的观察与取舍；维护者随后明确要求实际共享内容根，已采用的 0.4.x 方案见[新变更](../shared-content-and-lifecycle/adoption.md)。下述旧 `1.6/` 编辑源及当时不搬 Common 的判断不再定义当前布局；共享 C#／分开原生构建的决定继续保留。

## 结论：共享维护源，分开原生编译，按真实差异适配

**当前已经是一份 C# 源码、一份 Def／语言编辑源、两个原生构建产物，而非两套模组。** 推荐保留这个方向，不为目录对称性重写玩法，不把“源码共用”误写成“二进制必能共用”。需要进一步明确的是边界，而不是再抽一套空的通用框架。

维护者先接受共享源码＋分开原生构建，并要求利用 LoadFolders 隔离 VNPE 内容；当时的[窄范围方案](../vnpe-loadfolders/proposal.md)只改变可选接缝。随后维护者将范围扩大为实际 Common 运行根，采用与实施由[0.4.x 总计划](../shared-content-and-lifecycle/proposal.md)负责，本页保留原判断依据。

- 玩法、状态机、设置、奖励和扩展登记继续单源维护。
- 目标框架、游戏引用和必要 API／BCL 差异在构建及窄适配处处理；两版各产出 `Mwah.dll`，由加载目录互斥选择。
- 可选模组适配按外部依赖隔离，不按游戏 minor 再复制一份。
- 本轮不搬目录、不拆 DLL、不改 Job／Thought／设置的持久身份。将来出现真实差异时，先隔离该调用，再验证受影响消费者。

## 实际共享了什么，哪里确实分立

| 层面 | 观测到的实现 | 判断 |
| --- | --- | --- |
| C# 编辑源 | [Mwah.csproj](../../../Source/Mwah/Mwah.csproj) 默认纳入同一 `Source/Mwah/` 源码，无两套版本源码树 | 业务实现已经共用，无需再“提取”一次 |
| 原生编译 | 1.6 为 `net472`＋`Krafs.Rimworld.Ref 1.6.4871`；1.7 为 `net10.0`＋`1.7.4990-unstable` | 真实依赖接缝，保留两个目标 |
| BCL 适配 | [CallerArgumentExpressionAttribute.cs](../../../Source/Mwah/CallerArgumentExpressionAttribute.cs) 在 `!NET6_0_OR_GREATER` 时提供内部属性，新框架使用 BCL | 已有窄适配的合理实例；无需统一包装全部 API |
| Def／语言编辑源 | `1.6/Defs/`、`1.6/Languages/`；源码目录 `1.7/` 只放构建程序集 | 目录名有历史歧义，内容规则并未分叉 |
| 暂存包 | [stage-package.ps1](../../../scripts/stage-package.ps1) 从 `1.6/` 复制非 Assemblies 内容到两个 minor，再放各自 DLL | 分发副本不是第二个维护源 |
| 运行加载 | [LoadFolders.xml](../../../LoadFolders.xml) 为每个 minor 只选根及对应 minor；根不放运行内容 | 同一会话只加载一个版本的内容和程序集 |
| 构建渠道 | `MWAH_DEV`／`MWAH_STEAM`／`MWAH_GITHUB` 用于身份和日志；[build-runtime.ps1](../../../scripts/build-runtime.ps1) 按目标串行构建 | 渠道轴不等于游戏版本轴，不应乘出六套玩法 |

本轮只读现有编译产物的 IL：使用 `UnityEngine.Rect` 的引用在 1.6 产物指向 `[UnityEngine.CoreModule]`，1.7 产物指向 `[UnityStubs]`；旧框架的属性基类引用也与新框架环境不同。这支持保留原生编译边界。它不证明兼容桥绝无可能加载同一旧 DLL；若要改为单 DLL，仍需对应游戏的实际解析和运行证据，不能用源码相同代替。

## 整个模组的依赖和状态所有权

```text
右键／导演台／自主撮合
  → 共享准入、范围、冷却与占用判断
  → 配对 Job 或 descriptor 定义的非 Pawn Job
  → 接近／表演／一次结算／返程
  → 天意、思想／好感及适用的机器奖励

Def → 扩展 registry／天意内容 → 上述消费者
设置视图 → 规范设置值 → 准入和结算；持久化由现有设置入口负责
可选 VNPE adapter → 目标身份／站位策略 → 原有机器 Paste 结算
以上源码 → 1.6／1.7 原生编译 → 对应运行目录
```

这不是把所有 Verse 类型隔离出去的纯算法库。Pawn、Thing、Job、预订和 Scribe 就是该模组的领域对象及宿主合同；把它们逐属性转写成 `IPawn`、`IJob` 不会自动产生可维护的核心。

| 状态／责任 | 当前权威及寿命 | 跨版本处理原则 |
| --- | --- | --- |
| 资格、范围、命令入口 | `KissUtility`、`KissBoundary`、`KissScope` 与直接调用方 | 共同规则不按 minor 各写一次；引擎事实转换才适配 |
| 两个 Pawn 的协作与单 Pawn 扩展 | [JobDriver_Kiss](../../../Source/Mwah/Jobs/JobDriver_Kiss.cs) 与 [JobDriver_KissThing](../../../Source/Mwah/Jobs/JobDriver_KissThing.cs) 分别拥有本次 Job 的完成标志、进度和退出 | 两种 Job 因参与者责任不同而分立，不是版本重复；不强塞成一个巨型 driver |
| 非 Pawn 扩展身份 | [KissThingAddons](../../../Source/Mwah/Actions/Kiss/KissThingAddons.cs) 在 Def 加载期建立 registry；JobDef 元数据定位 worker | registry 选择、Job 生命周期和策略结算各司其职；旧 JobDef 含义保留 |
| 冷却／导演台残留 | 内存态；[KissTicker](../../../Source/Mwah/Systems/KissTicker.cs) 在建局／读档重建组件时清理 | 不在版本适配层复制字典或清理时机；不借整理改变冷却不落盘的合同 |
| 设置与视图 | `MwahMod.Settings` 为规范值；`MwahSettings.ExposeData` 持久化；视图编辑状态短寿命 | 保留提交→消费→保存连接，版本包装不另持配置副本 |
| 天意和记忆 | `KissFate`／Thought 内容与每个 Pawn 的原生记忆；机器策略只决定适用倍率和额外奖励 | 已保存的旁白、倍率、槽及一次结算仍按原含义；适配不另抽结果 |
| VNPE 目标缓存 | 基线的 `Source/Mwah/Compatibility/VanillaNutrientPasteExpandedCompatibility.cs` 在 Def 加载期检查包并缓存三个精确 Def；0.4.x 已由[通用登记消费](../../../Source/Mwah/Actions/Kiss/KissTargets.cs)替换，专有身份转入条件内容 | 缺少可选包不阻断基础能力；不复制为 VNPE16／VNPE17，不引入第三方类型泄漏 |

因此，共用层应是已有的规则和执行责任，不是一个拥有第二套 Pawn／冷却／记忆状态的“核心管理器”。

共享也发生在功能之间：`KissStage`、`KissReturn`、`KissActivity` 已为执行阶段、返程和活动识别提供共用责任，`MwahTime`、`KissFate` 与奖励实现复用时间和结算含义。这些因相同规则变化而聚合的部件，比分出一个按技术名词堆放的 Common 大目录更有价值。当前设置视图共编两版；若以后真的选择不同原生 UI 栈，应分开视图适配而保留同一设置值和提交／持久化连接，不复制整套设置模型。

## 用反例检验各个方案

### 反例一：保留两个输出，于是干脆复制两套源码

若只在 1.7 修复返程重复结算，或只在 1.6 修复机器单槽倍率，两个版本即使都能编译，也会违反等价请求的语义保证。源码分叉需要持续双向同步，却没有独立产品需求收益。**否决完整源码分立；保留的是 ABI／交付边界，不是玩法分叉。** 当前单源实现已经避免这类漂移。

### 反例二：相同源码，所以把同一个 DLL 放进两版

本轮观察到 `Rect` 的程序集引用不同；新框架还不需要旧框架属性 shim。将 1.6 DLL 直接冒充 1.7 DLL，可能在实际加载或 UI 调用时才暴露问题，即使源码检查完全通过。**当前不合并 DLL。** 若未来版本引用／加载合同实际收敛，而且单一产物通过两版原生消费、旧配置与存档验证，可以重审；不把今天的分立升格为永不改变的教条。

### 反例三：先拆 Mwah.Core.dll，所有引擎东西再经接口

奖励要操作原生 Need／Thought，Job 要遵守原生预订和取消，设置也用 Verse 生命周期。若核心为了“独立”复制这些事实，便需要同步身份和完成状态；一次结算标志在两个 owner 中漂移就可能双发奖。多一个 DLL 还增加加载及类型身份审查，而没有已知独立消费者。**否决现在拆核心 DLL。** 真正可独立复用的纯计算形成稳定边界、有实际消费者时再抽；小函数可先留在同一程序集。

### 反例四：把内容搬到 Common 就已经架构优化

源码内容原本就只有一份。只搬目录、不改 `$versionedSource = ... '1.6'`、语言／Def 扫描及说明，会产生“编译成功但包缺内容”；若同时加载 Common 和旧 minor 内容，则会重复 Def／翻译。**本轮不迁移。** 将编辑源改名为 `Content/` 以后可以消除历史歧义，但须一起调整暂存、审计和直接读者，保持原分发形状。将运行内容也改为只加载一次的 `Common/` 是另一项加载合同变更，不能混作目录整理。

当前磁盘上的两份暂存内容不会在同一游戏会话解析两次。没有体积或加载瓶颈证据，不值得仅为去掉分发副本改变已有效的加载链。

### 反例五：适配抽象必须先覆盖所有原版 API

若预先做巨大 `IGameApi`，真实游戏能力和错误路径会被藏在转发层；若新 wrapper 顺便要求所有旧墙／树请求也提供机器台位，则改变旧合法用法。**只适配发生变化的 API。** 当前可直接共编的 PowerOn、Food、Touch、Scribe 和 Job 行为不需要假分支；以后若方法签名或原生语义变化，再用局部条件编译、薄封装或局部实现转换，并保留旧入口、含义和条件。

### 反例六：可选模组兼容也按游戏版本拆两份

同一组 VNPE Def 身份若复制两处，之后只改一处就会出现版本特有漏识别。现有 adapter 既不引用 VNPE DLL，也不拥有其管网状态。**继续按可选依赖隔离。** 只有确认该依赖在两版实际提供不同合同，才在这个 adapter 内处理差异，不让整个机器执行链分叉。

## 后续变化的决策门槛

本轮没有必须实施的架构迁移。将来的最小动作由出现的压力决定：

- **具体原生 API 变了**：记录两版输入／输出差异，修改窄适配，复用共享规则；用既有双版本构建及该消费者的原生结果验收。
- **编辑源名称造成真实维护错误**：单独批准 `Content/` 源目录迁移；同一次完成复制、扫描、直接读者和包内容验证，运行包仍可保持原样。
- **决定改变运行加载结构或共用 DLL**：另立范围和恢复路径；验证目标游戏实际加载、Def、UI、配置／存档与关键 Job，不以新目录或编译成功验收。
- **未来并行构建**：目前脚本串行共用项目中间目录；并行化前再隔离各目标的中间输出／还原状态，不为未发生的并发增加平台。
